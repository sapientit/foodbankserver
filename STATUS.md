## Deployed

**A test system went live on 2026-08-08**, on the Cloudflare **free plan**, at
`https://foodbank-server.losttemple.workers.dev`. It is the top-level wrangler environment
(`npm run deploy:test`) against its own EU database, `foodbank-test` — separate from production's
`foodbank` for the same reason the two Google vars differ. All twenty migrations are applied,
`AUTH_JWT_SECRET` is set, and health, readiness, the public routes, dev-login and the scheduled-job
trigger were all verified against it.

It runs `AUTH_MODE=dummy`, so anyone knowing a seeded account's address gets an admin token. **It
must never hold real personal data.** The committed `pete@x.com` seed was changed on that database
after migrating.

Production has **no application deployed** and no database changes; `foodbank` still sits at
migration 0006. A `foodbank-server-production` Worker does exist on the account, but only as the
empty shell `wrangler secret put --env production` created on 2026-07-29 — no code, no route,
answers `404`. Its `AUTH_JWT_SECRET` is already set.

Deploys go through `~/bin/foodbank-deploy-server` (test by default; `--production` needs a typed
confirmation).

Three things the deployment established, all in
[`docs/operations/production.md`](./docs/operations/production.md):

- **A browser session cannot survive on `*.workers.dev`.** The refresh cookie is `SameSite=Strict`
  and both `workers.dev` and `pages.dev` are on the Public Suffix List, so client and API on those
  hosts are cross-site and the cookie is never sent. **Settled 2026-08-08:** the client Worker
  serves the app and proxies `/api/v1/**` here over a service binding, so everything is same-origin.
  `ALLOWED_ORIGINS` stays empty and nothing changes on this side — but the proxy must forward
  `cf-connecting-ip`, or the rate limiter collapses every visitor into one bucket and the referral
  form is capped at five submissions a minute for everybody. Requirements are in `API.md`; **this
  side cannot detect a breach of them.**
- **The extract needs a verifiable domain before go-live.** Testing-status consent works on
  `pages.dev`, but the Sheets scope is sensitive and publishing requires a domain Google can verify.
- **The free plan caps subrequests at 50 per invocation**, and SMS sending is one `fetch` per
  household — so a session over ~48 households cannot be texted in one go. The 10 ms CPU ceiling is
  **not yet proven**: the scheduled job has only run against an empty database.
- **Free-plan limits are per account, and this account also runs `losttemple-api`.** They share the
  100,000 daily requests; exceeding it returns error 1027 for _both_ Workers. Rate limiting was
  verified working (43 × `429` from 60 sequential posts against a 5/60s limiter) but is permissive
  and eventually consistent — a short burst gets through, so never assert an exact cutoff in a test.

## Implemented but awaiting configuration

These are written, tested and wired. They do nothing, or do less, until a value is set. **None of
them is a gap in the code.**

| Feature                  | State                                                                                                                                                                                                                | What it needs                                                                                                                                                                                                                                                                                      |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **PII purge**            | Runs nightly on the `17 2 * * *` cron and purges **nothing**. Clears the referee's own fields and `adminInfo`; the referrer's details and `reviewComment` survive. **One `UPDATE` per row** — see the warning below. | `PII_RETENTION_DAYS=365`. The period is settled at twelve months; the variable is still unset.                                                                                                                                                                                                     |
| **Turnstile**            | Verified on `POST /public/referrals` before parsing; **skipped when no secret is set**, which can only be development because production refuses to boot without one.                                                | A Turnstile widget and `TURNSTILE_SECRET_KEY`.                                                                                                                                                                                                                                                     |
| **CORS**                 | Allowlist middleware applied app-wide; with no origins configured it emits nothing, which is correct same-origin behaviour.                                                                                          | `ALLOWED_ORIGINS`, only if the frontend is on a different origin. Never a wildcard.                                                                                                                                                                                                                |
| **Rate limiting**        | Applied per route to all six public endpoints, keyed on `cf-connecting-ip`. The binding is **optional at runtime**, so it is inert in the test runner and in a plain `wrangler dev`.                                 | Nothing in code — the bindings are declared in `wrangler.jsonc`. It is live wherever the binding exists.                                                                                                                                                                                           |
| **Spreadsheet extract**  | All four routes are live and admin-only. With neither value set it reports `configured: false` and refuses a claim with a `422`, so nothing can be extracted until somebody configures it.                           | `GOOGLE_SHEETS_SPREADSHEET_ID` and `GOOGLE_OAUTH_CLIENT_ID` as `vars` in `wrangler.jsonc` — **neither is a secret**, and both differ per environment so a test deployment cannot touch the real spreadsheet. The OAuth client needs the Sheets scope and the frontend's origin. Blank means unset. |
| **Access token signing** | Refuses to start without a key.                                                                                                                                                                                      | `wrangler secret put AUTH_JWT_SECRET --env production`.                                                                                                                                                                                                                                            |
| **SMS reminders**        | Every route, the webhook and the 30-day purge are live. With no credentials the send path records **every household as a failure** rather than pretending — which is visible on the screen, not silent.              | `SMS_API_KEY`, `SMS_SENDER` (the reply number) and `SMS_WEBHOOK_SECRET`. Production refuses to boot without the last one.                                                                                                                                                                          |

**One hazard in the purge, for whoever sets `PII_RETENTION_DAYS`.** `purgeReferralPii` issues one `UPDATE` per
candidate row. That is fine on a nightly tick clearing a handful of referrals, but the **first** run
after `PII_RETENTION_DAYS` is finally set will face every referral older than the period at once —
months of history — and the free plan allows 50 queries per invocation. Set the period before there
is a backlog, or make the purge a single `UPDATE ... WHERE referred_at < ? AND pii_purged_at IS
NULL` first. This predates the referral review work and was not changed by it.

See [`docs/operations/production.md`](./docs/operations/production.md) for the full go-live
sequence.

| ------- | -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

## Not implemented

Tracked so it is not mistaken for finished work.

- **TheSMSWorks request and webhook shapes are read defensively, not verified.** The send call and
  the inbound payload parser accept several spellings of the provider's field names because no live
  account has been available to confirm them against. The tests pin our own behaviour, not theirs.
  **Verify both against a real account before go-live**, and simplify the parsing once they are
  known.
- **A session's `deliveriesAllowed` is recorded but not enforced.** An administrator can mark a
  session as taking no deliveries, and it is on both the staff and public session responses — but
  `POST /public/referrals` still accepts `isDelivery: true` against one. The referral form is
  expected to stop offering delivery meanwhile. Agreed with Pete on 2026-08-06 as a deliberate
  later fix, not an oversight; when it lands it should be a `422`.

- **No Google identity provider.** `AUTH_MODE=google` currently means "no way to log in". The
  contract is in place, so this is one file — see
  [`docs/architecture/authentication.md`](./docs/architecture/authentication.md).
- **Deactivating a user does not revoke their access token.** They lose access at the next refresh,
  so within fifteen minutes. Immediate lockout would need a query per request — the thing stateless
  JWTs exist here to avoid — or a revocation list. Neither is worth it until someone asks.
- **A pick list has no "sync".** It reports divergence from its referrals but does not add parcels
  for referrals that arrived afterwards; an admin handles those by hand.
- **Model parcels cannot express exclusions** (no pork, gluten free). Dietary needs reach the picker
  as words rather than as structure: the client composes them into the parcel's **pick-list
  information** at generation, and a team leader substitutes items by hand. The server never reads an
  answer to do it — since the client owns the form, it sends the finished text. Adding exclusions
  the model parcel understands is a v2 conversation with the charity, not a gap to be quietly filled
  in.

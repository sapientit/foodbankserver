| **16 — spreadsheet extract** | `modules/exports`, admin only. **The server never calls Google and holds no Google credential** — a service-account design was built and deliberately replaced. The administrator's browser gets its own Sheets consent and does every write; the server hands out `GET /extracts/config` (spreadsheet id + public OAuth client id, distinct per environment), reserves one confirmed unextracted session at a time under an **atomic, 10-minute claim** (`POST /extracts/claims`, returning every referral on it whatever its status), and records the write with `POST /extracts/claims/{claimId}/complete` — safe to retry, and it can never trigger a Google write. Claims expire so a closed laptop cannot block the queue; completing an expired or another administrator's claim is a `409`. **Expiry is the only way a reservation comes back** — there is no early-release route, so a browser that stops on a failed Google write leaves that session reserved for the full ten minutes, and the next claim skips it. That is why `claim: null` means "nothing could be handed out", **not** "the work is done": `remaining` is what tells the two apart, and reporting a null claim as "extract complete" would tell an administrator the spreadsheet is up to date when it is not. Settled by Pete on 2026-08-17 as documentation rather than a behaviour change — nothing is lost and nothing is sent twice. Pinned by `test/exports.test.ts`. Migration `0020` added `extracted_at` plus the three `extract_claim_*` columns. `toExtractRow()` is the allowlist; `answers` goes out as an object because the sheet's hidden metadata sheet owns the `answerKey → column` mapping, which is **not** in D1. **A claim's `stockItemUsage` array joined `rows` 2026-09-13**: one `{stockItemId, stockItemName, quantity}` entry per stock item the session actually issued, summed server-side (`stock.repository.ts`'s `sumIssuedByItemForSession`) from the ledger's current `parcel_issued` movements for the session — no new table, no flag on `stock_ledger`, no queue or reservation of its own, travelling under the same claim and the same `complete` as `rows` always has. A retired item still appears if it was issued for the session; a session that issued nothing returns `stockItemUsage: []`, not a missing field. `test/exports.test.ts`. |

| **18 — delivery windows** | A session's single delivery time became a **window**: `deliveryWindowStart` and `deliveryWindowEnd` on `sessions` and `recurring_sessions`, replacing `delivery_time` (migration `0024`). A van cannot arrive at 13:00, so a single time was a promise the round could not keep. The pair moves together and the end must be strictly after the start — both enforced in Zod, not in SQL, because both tables are foreign-key parents and SQLite cannot add a table-level CHECK to an existing table. A session setting no window delivers across **its own hours**, resolved in the pure `modules/sessions/delivery-window.ts` and read by both the mapper and the SMS composer. **`PublicSession` gained the window**, and carries the _effective_ one, never null — the narrowest response in the API, widened on purpose because the referral form now asks the referrer to confirm the client will be at home for the window and cannot ask that without stating it. Migration `0024` drops the old column rather than renaming it: a moment is not a window and a rename would leave every existing row half-set. Settled by Pete on 2026-08-16. |

| **19 — delivery capacity and hard stops** | `deliveriesAllowed` (a boolean, deliberately unenforced) is gone, replaced by `deliveryCapacity` — a number within a session's overall `capacity`, not a separate flag (migration `0025`, one-off backfill from the old flag: `true` → 8, `false` → 0). A collection is unaffected by delivery capacity however full it is. Both new stops are `409`s with no override, and both are scoped to the public form only — admin move/copy keep exactly their existing capacity-only warn-and-`acknowledgeOverCapacity` behaviour, and never gained a cutoff check. ## Deployed

**A test system went live on 2026-08-08**, on the Cloudflare **free plan**, at
`https://foodbank-server.losttemple.workers.dev`. It is the top-level wrangler environment
(`npm run deploy:test`) against its own EU database, `foodbank-test` — separate from production's
`foodbank` for the same reason the two Google vars differ. Every migration is applied,
`AUTH_JWT_SECRET` is set, and health, readiness, the public routes, dev-login and the scheduled-job
trigger were all verified against it.

It runs `AUTH_MODE=dummy`, so anyone knowing a seeded account's address gets an admin token. **It
must never hold real personal data.** The committed `pete@x.com` seed was changed on that database
after migrating.

Production has **no application deployed** and no database changes; `foodbank` still sits at
migration 0006. A `foodbank-server-production` Worker does exist on the account, but only as the
empty shell `wrangler secret put --env production` created on 2026-07-29 — no code, no route,
answers `404`. Its `AUTH_JWT_SECRET` is already set.

Deploys go through `~/bin/foodbank-deploy-server` (test by default; `--production` needs a typed
confirmation). `~/bin/deploy_foodbank` coordinates a full test release of both repos together: it
runs server and client checks (including the cross-repo API type comparison) up front, deploys the
server before the client so migrations land first, then verifies the deployed pair including the
client's `/api/v1/**` proxy. Each half also has its own `--tests-only` / `--deploy-only` /
`--verify-only` phase for working on one side alone.

Three things the deployment established, all in
[`docs/operations/production.md`](./docs/operations/production.md):

- **A browser session cannot survive on `*.workers.dev`.** The refresh cookie is `SameSite=Strict`
  and both `workers.dev` and `pages.dev` are on the Public Suffix List, so client and API on those
  hosts are cross-site and the cookie is never sent. **Settled 2026-08-08:** the client Worker
  serves the app and proxies `/api/v1/**` here over a service binding, so everything is same-origin.
  `ALLOWED_ORIGINS` stays empty and nothing changes on this side — but the proxy must forward
  `cf-connecting-ip`, or the rate limiter collapses every visitor into one bucket and the referral
  form is capped at five submissions a minute for everybody. Requirements are in `API.md`; **this
  side cannot detect a breach of them.**
- **The extract needs a verifiable domain before go-live.** Testing-status consent works on
  `pages.dev`, but the Sheets scope is sensitive and publishing requires a domain Google can verify.
- **The free plan caps subrequests at 50 per invocation**, and SMS sending is one `fetch` per
  household — so a session over ~48 households cannot be texted in one go. The 10 ms CPU ceiling is
  **not yet proven**: the scheduled job has only run against an empty database.
- **Free-plan limits are per account, and this account also runs `losttemple-api`.** They share the
  100,000 daily requests; exceeding it returns error 1027 for _both_ Workers. Rate limiting was
  verified working (43 × `429` from 60 sequential posts against a 5/60s limiter) but is permissive
  and eventually consistent — a short burst gets through, so never assert an exact cutoff in a test.

## Not implemented

Tracked so it is not mistaken for finished work.

- **TheSMSWorks request and webhook shapes are read defensively, not verified.** The send call and
  the inbound payload parser accept several spellings of the provider's field names because no live
  account has been available to confirm them against. The tests pin our own behaviour, not theirs.
  **Verify both against a real account before go-live**, and simplify the parsing once they are
  known.
- **No Google identity provider.** `AUTH_MODE=google` currently means "no way to log in". The
  contract is in place, so this is one file — see
  [`docs/architecture/authentication.md`](./docs/architecture/authentication.md).
- **Deactivating a user does not revoke their access token.** They lose access at the next refresh,
  so within fifteen minutes. Immediate lockout would need a query per request — the thing stateless
  JWTs exist here to avoid — or a revocation list. Neither is worth it until someone asks.
- **A pick list has no "sync".** It reports divergence from its referrals but does not add parcels
  for referrals that arrived afterwards; an admin handles those by hand.
- **Model parcels cannot express exclusions** (no pork, gluten free). Dietary needs reach the picker
  as words rather than as structure: the client composes them into the parcel's **pick-list
  information** at generation, and a team leader substitutes items by hand. The server never reads an
  answer to do it — since the client owns the form, it sends the finished text. Adding exclusions
  the model parcel understands is a v2 conversation with the charity, not a gap to be quietly filled
  in.
